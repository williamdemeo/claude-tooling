## Empirical test of both parts, in the environment this PR targets

Ran today (2026-07-28) in a **fresh Claude Code web sandbox** for this repo: recycled container, completely empty `/nix` (no nix CLI, no Agda — nothing). Nix 2.24.9 was bootstrapped by hand from `releases.nixos.org` (which the sandbox proxy allows, as it does `cache.nixos.org` and `cache.iog.io`), then both halves of the PR were exercised.

### Results

| # | Scenario | Command | Result |
|---|---|---|---|
| A | **master flake** (`github:` inputs), web sandbox | `nix develop --command true` | **Fails in <1 s** — first input fetch (`flake-parts` tarball) gets HTTP 403 from the session proxy: *"GitHub access to this repository is not enabled for this session"* |
| B | **this PR's flake**, stone-cold empty store (= fresh container, no prefetch) | `nix develop --command agda --version` | **≈ 90 s**, success: `Agda version 2.8.0`. All inputs resolved over `git+https`; ~5.6 GB / 110+ store paths substituted from `cache.nixos.org` + `cache.iog.io` (including `fls-agda` — nothing compiled locally) |
| C | same command again, warm store (= every session, if the prefetch ran in the setup snapshot) | same | **2.2 s** |
| D | `prefetch-devshell.sh` itself | — | idempotent; 4.3 s when warm; pins the GC root at `~/.cache/fls/devshell-profile` |

Direct endpoint probes confirm the mechanism: `codeload.github.com` / `api.github.com` → **403** for any repo not attached to the session, while `git ls-remote https://github.com/input-output-hk/agda.nix` succeeds through the same proxy.

### Reading of the results

- **Part 1 (flake `git+https`) is the on/off switch**, not an optimization: without it `nix develop` is impossible in web sessions (A vs B); with it, and identical narHashes, it's a no-op on unrestricted networks.
- **Part 2 (prefetch) buys 90 s → 2 s per fresh container** — modest in the happy path. Its larger value is *risk placement*: the 90 s figure assumes `cache.iog.io` has everything (it did today). After a flake bump and before CI repopulates the cache, "cold" means local GHC/Agda builds — that cost lands in the snapshotted setup phase instead of an interactive session. Note the two parts are separable: part 1 must live in the repo; the prefetch invocation could alternatively live only in the web environment's setup-script config.
- A useful bonus fetch avoided: nix substituted the **nixpkgs source by narHash** from the binary cache, so the feared full nixpkgs clone never happened.

### 🐛 One real bug found while testing

Claude-web clones are **shallow**, and nix's git fetcher errors on shallow repos while walking parent commits:

```
error: getting parent of Git commit '…': object not found - no match for id (…)
```

`prefetch-devshell.sh` invokes `nix develop` against the git checkout, so **as written it fails in the very setup phase it targets**. One-word fix: invoke `nix develop --profile "$GCROOT_DIR" path:"$REPO_ROOT" --command true` (the `path:` fetcher bypasses git). Demo B above was run via `path:` for exactly this reason.

### Suggested follow-ups for this PR

1. Switch the script (and the README's examples) to `path:"$REPO_ROOT"`; mention the shallow-clone behavior.
2. Add `shallow = true` to the `nixpkgs` input as a fallback for when source substitution misses.
3. README: state explicitly that the setup script must **install nix first** (the script deliberately no-ops without it — correct behavior, but the sequencing should be spelled out), and that a root/single-user install needs `build-users-group =` + `sandbox = false` (or use the official installer, which handles it).
4. Out of scope here but the natural companion: the same setup phase should restore the latest CI `_build` artifact — the dev shell provides the compiler in seconds, but first-typecheck latency is dominated by the `.agdai` interface cache, not the toolchain.
